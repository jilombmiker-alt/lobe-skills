# 产品拆解skill：证据驱动的逆向方法

把分散的产品材料转成一套可审计、可解释、可迁移的模型。目标不是复述页面，也不是猜内部实现；目标是回答：**用户经历了什么、系统如何显性运作、哪些机制可以复用、还需要验证什么。**

## 总原则

1. 先建证据账本，再下结论，再画流程或写规则。不得反向用预设流程筛选证据。
2. 严格区分：
   - 【页面事实】直接可见的文字、控件、状态、资产、时间、结果或报错。
   - 【合理推断】由多条事实支持的机制假设；写出依据与不确定性。
   - 【尚未确认】材料不足、互相矛盾，或必须通过操作/接口/更多录屏才能确认。
3. “规划完成”“正在思考”“已完成”仅是用户可见摘要；不是隐藏思维链，也不是工具已执行的证明。
4. 聊天、画布、资产库、任务状态、预览和下载是不同证据面。任何冲突都要保留，不得替产品选一个“真相”。
5. 不编造官方字段名、工具名、模型、权限、计费、安全规则或重试机制。未公开名称使用语义化占位符，并标注“非官方命名”。
6. 输出应服务于用户的当前问题。不要因为能分析 Agent，就在只需要用户旅程时自动扩展到 Prompt。

## 交付模式与标准范本

先根据用户目标和材料选择模块；可以组合，但每一模块都必须能回指证据。用户明确指定“本轮只做一个目标”“先停止”等范围时，严格按该范围交付并停止。

| 用户要解决的问题 | 选择模块 | 最小交付 |
|---|---|---|
| 体验是否顺、用户哪里会卡住 | 用户旅程 | 时间线、决策点、状态变化、阻力与机会 |
| 产品到底有哪些步骤、依赖和分支 | 流程与状态模型 | 主流程、例外路径、状态机、输入/输出 |
| AI/自动化谁在做什么 | Agent 与运行契约 | 可归因 Agent、输入/判断/工具/输出/交接 |
| 想复现一个可见 Agent 的行为 | 功能等价 Prompt | 边界问答、I/O 协议、状态机、规则追溯、测试；非官方 Prompt |
| 想比较版本或竞品 | 对比分析 | 统一维度下的事实对照与差异假设 |
| 要一份详细的用户流程、导航或 AI 功能报告 | 深度体验报告 | 核心结论、证据账本、架构、路径、反馈、问题、机会、验证清单 |

默认完整拆解按三阶段推进：

1. **用户旅程**：用户实际经历了什么，以及可见的反馈、选择和阻力。
2. **Agent 契约与数据流**：哪些 Agent 可被归因，它们怎样读、判断、写和交接。
3. **目标 Agent 的功能等价 Prompt**：只在用户指定 Agent 后进行；不是官方 Prompt。

用户可只调用其中一阶段；用户明确要求一次性完整交付时可连续执行。每阶段的固定栏目、HTML 表格和流程图要求见 [references/analysis-modules.md](references/analysis-modules.md)。

## 标准工作流

### 1. 建立调查边界与材料清单

1. 明确产品、目标用户、要回答的问题、时间范围和希望的交付形式。
2. 枚举全部材料：截图、录屏、页面、聊天、原型、说明文档、已有分析与最终产物。为每份材料保留来源、时间/顺序、可见范围。
3. 从最早可见事件开始排序；材料不足以排序时，标“顺序未确认”。
4. 先声明不可访问区域和无法验证的关键问题。不要以“常见产品做法”填空。

### 2. 抽取证据并建立账本

逐份检查可交互元素和系统结果，而不只读聊天文案：按钮、表单、默认值、禁用态、空态、错误、确认门、状态标签、画布、资产、预览、编辑/重试/返回入口。

优先沿用材料已有的截图/时间编号（如 `S01`、`00:35`）；没有时再分配稳定 `E01`。记录“原文/对象—发生位置—可见变化—证据等级”。同一事实可被多个分析模块引用。详细格式见 [references/evidence-and-quality.md](references/evidence-and-quality.md)。

### 3. 重建可观察过程模型

以“事件—判断—状态—产物”而不是页面菜单来组织：

1. 事件：谁做了什么，或系统显示了什么变化？
2. 判断：用户/系统是否要选择、确认、修正或等待？
3. 状态：任务、资产、页面分别进入什么可见状态？
4. 产物：生成/修改/引用/缺失了什么？谁可继续使用？
5. 分支：正常、修改、失败、取消、权限/额度受限等。没看到的分支只列为验证项。

先建立主线，再补分支；不要把多个不同时点的截图拼成一条已证实的连续执行记录。

### 4. 按需深入模块，并套用标准交付契约

- **用户旅程**：先声明范围边界；逐阶段输出用户目标、截图可验证动作、页面可见反馈、反馈类型、下一步行为和证据；再画泳道与反馈观察。用户要求“报告 / 详细 / 导航设计 / AI 功能 / 用户流程”时，切换到深度体验报告而非压缩成一张表。
- **流程与状态**：聚焦前置条件、状态转移、依赖、回退、并行与终态。
- **Agent 契约**：只有“回复/交接/资产变化/状态变化”能归因时才认定 Agent 出现；每个 Agent 都检查六类输入、十项契约问题、工具、五类输出、读写字段与下游交接。
- **功能等价 Prompt**：只针对已选择的一个 Agent；先输出十项边界问答、输入/输出/工具契约和状态机，再写 Prompt、规则追溯与最小测试。将工程增强规则写为建议，绝不伪装成页面事实。

模块级模板与判断问题见 [references/analysis-modules.md](references/analysis-modules.md)。深度报告必须把“页面事实、合理推断、尚未确认”分别落到结论、流程和建议中，不得以篇幅为由省略证据账本或未知项。

### 5. 通过质量门后交付

交付前逐项检查：覆盖、可追溯、一致性、边界、可行动性。任一关键门未通过时，输出“当前结论 + 证据缺口 + 最小补证动作”，不要给确定性结论。详见 [references/evidence-and-quality.md](references/evidence-and-quality.md)。

## 分支规则

- **材料缺失或顺序不明**：先给材料地图和补证清单；不强行绘制端到端流程。
- **状态冲突**：并列记录冲突来源，分析影响范围，列出最小验证动作；不得用 Agent 话术覆盖资产事实。
- **未见失败/中断/额度**：不把它们画成已实现能力；可作为风险假设与待测路径。
- **用户修改上游内容**：分别检查是否出现版本、失效、重生成或引用变化；没有证据时不假定自动级联。
- **只出现 Agent 名称**：名称本身不证明已运行。只将可归因行为纳入 Agent 清单。
- **用户要求“官方 Prompt/工具调用”**：说明无法从页面获取；可提供标明证据等级的功能等价设计。
- **用户要求 HTML、表格或流程图**：服从指定格式；图中每个关键节点必须带证据 ID，未证实分支使用虚线或明确的“尚未确认”。
- **只要正常路径**：仅交付有证据的主链路、正向/中性/负向可见反馈；把失败、退款、重试等排除到范围边界，不补写。
- **要求完整异常路径**：先查找失败、取消、重试、额度、安全拦截、空态和恢复入口；如果没有材料，交付“尚未确认的分支与补证计划”，而不是完整虚构状态机。

## 交付协议

1. 先给“查看范围与证据缺口”，再给结论；事实、推断、未知始终可辨。
2. 按所选模块使用标准栏目与表头，不可只给散文总结。HTML 交付必须包含可读表格、图例、证据编号和图中关键节点的证据标记。
3. 用户要求分轮时，在每轮范围结束后停止等待确认；没有明确要求时，默认先完成用户旅程，再询问是否进入 Agent 契约。
4. 所有流程图必须区分正常、修改和异常的实际证据状态；未被观察的路径不伪装为事实。
5. 产品建议要连接到具体机制和证据，格式为“问题 → 影响 → 机会 → 验证方式”，避免通用建议。
6. 功能等价 Prompt 的完成条件不得只依赖自然语言“完成”；必须包含结果存在、状态写入、验证与交接（仅在证据支持该职责时要求）。

## 结束检查

- 每个关键结论能否定位到 `E` 编号、页面原文、控件或资产？
- 是否把计划、执行成功、状态写入和最终交付分开？
- 是否验证了用户真正能拿到的结果，而不仅是页面口头承诺？
- 是否把可迁移逻辑与该项目的偶然细节分开？
- 是否保留了无法证实的空白，并给出了下一步最小验证动作？
