# 产品拆解三步法

将页面证据逐层收敛为：用户经历、可见的 Agent 契约、可运行的功能等价设计。目标是理解产品行为，绝不冒充拿到了内部实现。

## 先建立证据边界

1. 按时间顺序查看全部页面材料；同时检查聊天、按钮、表单、任务状态、画布、资产库、预览、错误与可编辑入口。
2. 为每条结论标注：
   - 【页面事实】：页面可直接看到的文字、控件、状态或资产。
   - 【合理推断】：由两条以上事实推出的关系或流程。
   - 【尚未确认】：截图、录屏或页面没有足够证据。
3. 不把“思考完成”“规划完成”当作隐藏思维链，也不把计划话术当作已发生的工具调用。只有资产、状态、明确工具结果或后续页面变化能确认动作完成。
4. 不把聊天中的“已完成”当作交付完成；交叉核验画布资产、资产库、预览及下载结果。若冲突，保留冲突。
5. 未见余额不足、重试、中断、安全拦截、版本机制或角色参考图时，明确写为“尚未确认”，不要补写为能力。

## 工作流

### 第一步：用户旅程取证

目的：回答用户从输入需求到最终交付实际经历了什么。

1. 从最早消息提取用户初始需求：故事/任务、剧本、风格、参考素材、表单选择。
2. 逐个阶段记录：用户目标、用户动作、页面反馈、需做的选择、页面/资产变化、阻力、证据编号。
3. 标出所有判断门：满意/不满意、继续/中断、方案选择、成功/失败、余额充足/不足。未观察到的分支以虚线或“尚未确认”呈现。
4. 比对聊天、画布、资产库、任务状态与最终输出。把不一致单列为问题，不擅自裁决哪一方正确。
5. 交付证据表和三泳道图：用户、产品界面、系统结果。可附用户情绪、痛点和机会点，但情绪必须标为合理推断。

### 第二步：Agent 契约取证

目的：只识别当前场景中真正出现且可归因的 Agent，并建立其输入—判断—工具—输出—交接关系。

1. 先列 Agent 名单和时间顺序。名称仅出现于下拉菜单、任务标签或头像，但没有可归因的回复、资产或状态变化时，不把它算作已出现 Agent。
2. 对每个 Agent 检查六类输入：
   - 用户当前输入；用户长期信息；项目全局上下文；上游 Agent 输出；平台公共资产/知识/规则；工具与运行时结果。
3. 对每个输入逐项记录“是否可见、谁生产、当前 Agent 怎样使用、是否必需、证据等级”。不得默认所有字段存在。
4. 总结可观察判断：解决什么问题、何时自动继续、何时等待确认、何时停止、如何应对修改、异常和完成条件。不得复写隐藏推理。
5. 工具名未公开时用功能性名称，并显式注明“非官方工具名”。分别标明：页面结果确认、仅计划/摘要可见、尚未确认。
6. 输出每个 Agent 的 I/O 契约卡，并建立全局字段表和生产者—消费者关系表。特别检查版本、多源状态、资产引用和上游修改导致的失效。

### 第三步：单 Agent 功能等价 Prompt

目的：基于一位目标 Agent 的可见行为，设计可复现其工作流边界的 Prompt；不是还原官方 Prompt。

1. 只收集目标 Agent 的全部可见记录；区分直接截图证据和文件整理元数据。
2. 先写输入、输出、工具与状态机契约，再写 Prompt。若输入/输出/工具/状态不清，不要先写完整 Prompt。
3. 把规则分为【事实规则】【推断规则】【建议规则】【未知】。建议规则用于让功能等价 Agent 更稳定，不得写成原产品事实。
4. Prompt 必须明确：身份、目标、边界、输入协议、全局上下文读写、状态机、工具前置条件、显式确认、读回验证、版本/回退、失败/中断、下游交接、完成条件、输出格式。
5. 采用语义化占位字段和占位工具名，例如 `<创建项目计划草案>`、`project_brief_draft`；注明它们不是官方字段/接口。
6. 设计最小测试集：正常、缺输入、局部修改、工具失败、用户中断、全局状态冲突。测试必须写出“不允许出现的行为”。

## 对话框架与停止点

默认将三步拆成三轮，不在用户确认前跳到下一步；用户明确要求合并交付时才连续执行。

### 第一轮：用户旅程

按以下顺序输出：

1. 本次查看范围。
2. 无法访问或无法确认的证据。
3. 用户旅程证据表。
4. HTML 格式用户旅程图：三条泳道（用户、产品界面、系统结果），包含正常、修改/纠偏、失败与中断路径；每个节点写证据编号。
5. 用户情绪、想法、痛点和同类产品机会点；情绪必须标为推断。
6. 三个最值得讨论的体验问题。
7. 停止，等待用户确认；不继续拆 Agent、System Prompt、工具或全局上下文。

### 第二轮：Agent 契约

按以下顺序输出：

1. 查看范围与证据缺口。
2. Agent 清单（只记录可归因的实际出现 Agent）。
3. 每个 Agent 的 I/O 契约卡。
4. 工具总表。
5. 全局上下文字段表。
6. 数据生产者—消费者关系表。
7. Agent 输入—判断—工具—输出—交接流程图，并写能力边界备注。
8. 事实、推断和未知事项清单。
9. 最值得继续验证的五个问题。
10. 停止，等待用户选定要进入第三轮的目标 Agent；不直接写完整 System Prompt。

### 第三轮：单 Agent 功能等价 Prompt

按以下顺序输出：

1. 目标 Agent 的证据范围及十项边界问答（目标、接管、触发、交接、属于/不属于、修改重触发、停止、自动继续、确认）。
2. 输入契约（六类来源）。
3. 输出契约（五类输出）。
4. 工具契约（名称为功能命名时注明“非官方工具名”）。
5. 状态机及 Mermaid 状态图。
6. 事实规则、推断规则、建议规则、未知事项。
7. 功能等价 System Prompt。
8. 规则—证据追溯表。
9. 最小测试集：正常、缺输入、局部修改、工具失败、用户中断、全局状态冲突。
10. 仍然无法确认的问题。
11. 停止，不继续拆其他 Agent 或修改原产品页面。

需要完整表格、I/O 卡片、状态机语法和测试模板时，读取 [references/output-templates.md](references/output-templates.md)；需要逐轮交付与停止语句时，读取 [references/conversation-framework.md](references/conversation-framework.md)。

## 交付检查

- 每个结论是否有截图编号、页面原文、按钮/资产/错误信息？
- 计划和执行结果是否分开？
- 聊天与画布/资产/预览是否交叉核验？
- 是否把“未知”留空而没有填补？
- 功能等价 Prompt 是否禁止越权生成下游资产？
- 是否在完成后按用户要求停止，而没有继续拆不在范围内的 Agent、Prompt 或工具？
